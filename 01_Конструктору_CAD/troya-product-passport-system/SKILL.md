# Паспорт изделия (ПС/РЭ)

Паспорт не правят руками в Word: его собирает генератор. Данные изделий (тексты, характеристики, комплектность,
шаги сборки) записаны в `products.py`, общие разделы — в движке, рисунки строятся скриптами. Такой подход
выбран потому, что паспорт пересобирают после каждого ответа пользователя. Генератор даёт одинаковую вёрстку
во всех изделиях, сохраняет переносы и позволяет переиздать выданный паспорт тем же кодом.

Рабочий пример — 8 паспортов лабораторной мебели по СЗ № 794-М (`examples/lab_furniture_sz794`): там есть
изделия с мойкой, электрикой, вытяжкой, поставкой двумя частями. Для стульев и парт — пример
`examples/school_chair_nomad`: три стула Nomad (плавная и ступенчатая регулировка), рисунки из пошаговой
схемы сборки, буквы деталей в колонке «Рис.». Прежде чем писать новое изделие, найти в примерах похожее
и взять его формулировки за образец.

Шаблон оформления сделан из паспорта стула Nomad (обложка TROYA с рамками, A5, Times New Roman 11 пт).
Тексты разделов для школьной мебели сверены с генератором паспортов 840 (стул ученический регулируемый).

## Что где

| Путь | Что это |
|---|---|
| `scripts/new_project.py` | заводит папку генератора: копия движка, шаблона, заготовок |
| `scripts/engine/` | движок: `passport_lib.py` (вёрстка docx, переносы), `common.py` (общие разделы 4.1, 5–14), `build.py` |
| `scripts/figures/` | `iso.py` — изометрия по ГОСТ 2.317, `sch.py` — схемы по ГОСТ 2.721/2.755 |
| `scripts/check/` | `docx2pdf.ps1`, `fill_report.py`, `render_pages.py`, `yellow_report.py`, `print_booklet.ps1` |
| `templates/` | `Шаблон_паспорта_TROYA.docx` (обложка TROYA, A5), заготовки `project/products.py`, `project/figures/fig_01.py`, `project/README.md` |
| `references/product_data.md` | все ключи данных изделия, состав и порядок разделов, нормативка — **читать перед заполнением products.py** |
| `references/rules.md` | правила содержания (источники, номинал, шифр, цвета, жёлтое, электрика) — **читать всегда** |
| `references/figures.md` | какие рисунки нужны, API iso.py и sch.py, приёмы — читать перед рисунками |
| `references/checks.md` | вёрстка, порядок проверки PDF, как чинить переносы — читать перед выдачей |
| `examples/lab_furniture_sz794/` | рабочий пример: `products.py`, `figures/fig_*.py`, README с решениями пользователя |
| `examples/school_chair_nomad/` | стулья ученические: ключи школьной мебели, `fig_nomad.py` — рисунки из листов PDF схемы сборки |

Нужно: Python 3 с `python-docx`, `Pillow`, `pymupdf`; Microsoft Word (для PDF); шрифт `GOST_BU.ttf`.
Python запускать `python -P -E` (не `-I`: pymupdf стоит в пользовательских site-packages).

## Порядок работы

### 1. Понять задачу

Для каждого изделия выяснить шифр и наименование, основание (СЗ, заказ, ТЗ) и куда класть готовые
паспорта. На ПК владельца паспорта лежат в `<WORK>\07_Документация_изделий\01_Паспорта\<тема>`, заказ —
по навыку `kto-folders`. Если генератор по этой теме уже есть (`<WORK>\99_Служебное\Паспорта_*`),
продолжать в нём, а не заводить новый: в его README записаны решения пользователя.

### 2. Собрать источники

Источники в порядке доверия (подробно — `references/rules.md`):
- слова пользователя;
- схемы сборки и модели bCAD (`03_Корпус\02_Схемы сборки`, `01_Модели\*.bdf`, рендеры с фурнитурой);
- КД SolidWorks / КОМПАС (`02_Металл`, PDF чертежей);
- фото изделия;
- каталог и прайс TROYA — для масс и упаковки;
- текст СЗ.

Покупные изделия (смесители, мойки, вентиляторы, светильники, АВДТ) брать из Ограничительного перечня
(навык `troya-material-query-system`), функциональные размеры школьной мебели — по навыку
`troya-school-furniture-dimensions`, шифры — по шифратору TROYA (`cad-decimal-cipher-system`).

Найденное записывать в README проекта (раздел «Источники»). Чего нет ни в одном источнике, писать в `[[…]]`.
Если задачу можно разбить на независимые части (разбор КД разных изделий, поиск крепежа в архиве), отдать
их субагентам параллельно. Их выводы сверять со словами пользователя: слова пользователя важнее.

### 3. Завести проект

```
python -P -E <навык>\scripts\new_project.py "<WORK>\99_Служебное\Паспорта_<тема>_<ГГГГ-ММ-ДД>"
```

Генератор — служебный инструмент, поэтому у владельца он лежит в `99_Служебное`, а не рядом
с документами. На чужом ПК выбрать рабочую папку вне папки документов. Папка проекта самодостаточна
(движок скопирован): выданные паспорта пересобираются тем же кодом, даже если навык изменится.

### 4. Заполнить products.py

Ключи описаны в `references/product_data.md`. Ниже по разделам паспорта: что писать и откуда брать.
- **Раздел 1 «Общие данные»** (`general`) — назначение и ТР ТС/ГОСТ, конструкция по узлам, материалы
  с толщинами, оснащение. Без цветов и без отсылок к другим изделиям.
- **Раздел 2 «Технические характеристики»** (`specs`) — габарит номинальный, номер по ГОСТ, узлы, электрика,
  нагрузка, масса, упаковка.
- **Раздел 3 «Комплектность»** (`kit`, `kit_notes`) — строки по упаковочным местам и узлам. Номер строки
  равен позиции на рисунках. Крепёж с количеством перечислить в `kit_notes`, там же написать, что в
  комплект не входит.
- **Раздел 4 «Сборка и монтаж»** (`assembly`) — пункты в повелительном наклонении. В каждом пункте указать
  деталь (поз. N), крепёж и рисунок. Операции, сделанные на заводе, не описывать. Подключения включаются
  ключом `connections`.
- **Признаки** (`hpl`, `doors`, `chem`, `connections` …) сами включают нужные абзацы в разделы 5–14.
- **Стул, парта** — ключи раздела «Ключи для стульев, парт и школьной мебели» в `references/product_data.md`
  (`doors=False`, `wood=False`, `floor_parts`, `misuse`, `wear` …). Крепёж — по модели, схеме сборки и КД
  одновременно: если они расходятся, спросить пользователя, а не выбирать самому.

### 5. Рисунки

По одному скрипту `figures\fig_<ключ>.py` на изделие или семейство изделий (образец `fig_01.py`). Если у изделия
уже есть пошаговая схема сборки (PDF), рисунки комплекта и шагов вырезать из её листов, как в
`examples/school_chair_nomad/figures/fig_nomad.py`, а не рисовать заново: буквы и вид совпадут со схемой. Состав
рисунков и приёмы описаны в `references/figures.md`. Геометрию брать из КД в номинальных размерах. Позиции
ставить по таблице комплектности. Крепёж узлов брать по модели bCAD. Запуск:
`python -P -E figures\fig_<ключ>.py figures\out`.

### 6. Собрать и проверить

```
python -P -E build.py "<папка вывода>" [ключи]
powershell -ExecutionPolicy Bypass -File <навык>\scripts\check\docx2pdf.ps1 -Src "<папка вывода>" -Out "<временная папка>"
python -P -E <навык>\scripts\check\fill_report.py "<временная папка>"
python -P -E <навык>\scripts\check\render_pages.py "<pdf>" 3-7 "<png>"
python -P -E <навык>\scripts\check\yellow_report.py "<папка вывода>"
```

Страницы с меткой LOW и страницы вокруг правки посмотреть глазами. Как чинить — `references/checks.md`.
PDF копировать к docx только после проверки и только если файл не заблокирован у пользователя.

### 7. Отчитаться

Коротко: что сделано по каждому изделию и где файлы. Затем вопросы по жёлтому. Изделия в вопросах называть
шифром и наименованием, а не номером позиции СЗ. Для каждого вопроса указать, что сейчас стоит и откуда.
Пример:

> **ТМ.М2.0003 «Тумба лабораторная с мойкой»** — нагрузка на столешницу стоит 10 кг (в СЗ нет, взято по
> аналогу). Подтвердите или дайте значение.

### 8. Правки по ответам

1. Скопировать `products.py` и затронутые `fig_*.py` в `Архив` проекта (`<файл>_до_<что меняем>.py.bak`),
   прежние PNG — в `figures\out\Архив`.
2. Скопировать выданные docx/pdf затронутых изделий в `_Аннулировано\До_<что меняем>_<ГГГГ-ММ-ДД>` рядом
   с паспортами. Это копии, оригиналы не удалять.
3. Внести правку, убрать `[[…]]` у подтверждённого, пересобрать только затронутые ключи и проверить
   по шагу 6, сравнивая с прежним PDF.
4. Записать решение с датой в README проекта.

## Чего не делать

- Не править выданный docx в Word вместо `products.py`: следующая сборка сотрёт правку. Если пользователь
  правил docx сам, сначала перенести его правки в `products.py`.
- Не менять гарантию, сроки службы, сроки и данные изготовителя по своей инициативе.
- Не закрывать Word и просмотрщик PDF пользователя: `docx2pdf.ps1` работает в своём экземпляре Word.
- Не удалять прежние версии документов: их место — `_Аннулировано` и `Архив`.
- Не класть скрипты и временные файлы в папку с документами и не включать их в комплект передачи.
